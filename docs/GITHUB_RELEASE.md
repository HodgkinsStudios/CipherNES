# Publishing CipherNES 1.0.0

This checklist covers **HodgkinsStudios/CipherNES** and the binaries generated by its GitHub Actions workflows. The source tree and release assets must refer to the same emulation-code revision.

## 1. Verify the source and build results

1. Confirm the public source repository includes `.github/workflows/`, `.github/ci/`, licenses, and the documented build scripts.
2. Open [GitHub Actions](https://github.com/HodgkinsStudios/CipherNES/actions). Inspect the latest run for each distribution target and verify it completed successfully.
3. Check the job logs for compiler failures, failed smoke tests, missing runtime DLLs/frameworks, and packaging errors.
4. Download the artifacts produced by **one common source revision**. Do not mix binaries built from different emulation-code versions without documenting the difference.

### Verified CI baseline (October 22, 2026)

Commit `a65eee4551eb24405672bc789e13ca66e215a72d` successfully completed **Ubuntu, Windows, macOS, AppImage, Debian, and Flatpak** workflows. The macOS matrix produced independent Intel (`x86_64`) and Apple Silicon (`arm64`) archives.

| Deliverable | Intended users |
| --- | --- |
| Ubuntu x86_64 ZIP | Linux desktop users installing manually |
| Windows x86_64 ZIP | Windows users; includes one self-contained .exe |
| macOS x86_64 ZIP | Intel Mac users |
| macOS arm64 ZIP | Apple Silicon Mac users |
| Linux x86_64 AppImage | Portable Linux desktop application |
| Debian/Ubuntu amd64 `.deb` | Debian-family package installation |
| Linux x86_64 `.flatpak` | Flatpak users with the necessary runtime |

CI build success **does not establish physical-hardware certification**. Before marking a release fully validated, check audio output, ROM dialogs, controller mapping, fast-forward, rewind audio, save states, display switching, and macOS security prompts on representative devices. Flatpak file-picker portal behavior requires special attention.

## 2. Prepare a release

- Make sure the documented **AccuracyCoin 146/146** result and its screenshot are properly described as recorded evidence, not a new test of every platform.
- Keep external game ROMs, firmware, save files, and third-party test images out of the release.
- Read [validation details](VALIDATION.md) and confirm the release notes correctly distinguish the 289-ROM load/state smoke check from internal ROM PASS verdicts.
- Generate SHA-256 checksums for each downloadable artifact and preserve an accompanying manifest.
- Retain `THIRD_PARTY_NOTICES.md` and `LICENSE`.

## 3. Publish

1. Create or verify tag `v1.0.0` on the intended release commit.
2. Create the GitHub release titled **CipherNES 1.0.0**.
3. Use [`RELEASE_NOTES_1.0.0.md`](../RELEASE_NOTES_1.0.0.md) as the release description and attach the seven platform-specific downloads and checksums.
4. Review the public release page and test representative download/install paths.

GitHub automatically provides source archives for every tagged release.

## Per-user runtime changes

Saves, states, screenshots, TAS files, captures, config, and FDS BIOS are loaded from the per-user `HodgkinsStudios/CipherNES` data root on each platform. All packaged `bios` directories are created at runtime. For Linux, prefer AppImage when promising a single-file install: the unbundled native ELF still uses system SDL2 and zlib.
